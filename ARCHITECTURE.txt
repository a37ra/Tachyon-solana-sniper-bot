# Архитектура SOLANA_BOT

Источник истины по числам и формулам — корневое ТЗ (`tz-solana-sniper-bot-production.md`).
Этот документ описывает, как разделы ТЗ отображаются на процессы/крейты репозитория.

## Три процесса, три уровня доверия

```
┌─────────────────────┐        UDS + signer.proto        ┌──────────────────────┐
│   solbot-strategy    │ ───────────────────────────────▶ │    solbot-signer      │
│  (нет ключей вообще)  │ ◀─────────────────────────────── │ (единственный держатель │
│                       │      SignerIntentResponse         │  приватного ключа,     │
│  actor/*  signal/*    │                                    │  mlock, systemd strict)│
│  risk_gate/* sizing/* │                                    └──────────────────────┘
│  exit/* routing/*     │
│  circuit_breaker/*    │        внутренний event bus (solbot-notify)
│  smart_money/*        │ ───────────────────────────────▶ ┌──────────────────────┐
│  state/* (SQLite)     │                                    │   solbot-telegram      │
└─────────────────────┘                                    │ (алерты + admin-      │
                                                             │  команды оператора)   │
                                                             └──────────────────────┘
                       ▲
                       │ manual_cli_command (control_lane)
              ┌──────────────────┐
              │    solbot-cli     │  (то же самое управление, но с терминала — 6.)
              └──────────────────┘
```

Разделение на три процесса — не техническая прихоть, а прямое следствие 3.1:
`solbot-strategy` должен иметь возможность падать, зависать, содержать баги в
логике сайзинга/роутинга — и ни один из этих сбоев не должен быть способен
скомпрометировать приватный ключ, потому что ключ физически не находится в
адресном пространстве этого процесса.

## Two-Lane Actor (2.1) — `crates/solbot-strategy/src/actor/`

Один актор на mint. Канал актора разделён на два lane с разной семантикой
переполнения — см. `actor/mod.rs` (типы), `actor/control_lane.rs` и
`actor/market_data_lane.rs` (обработчики), `actor/mint_actor.rs` (`tokio::select!
biased`, control_lane всегда опрашивается первым).

Ключевое: `control_queue_wait_deadline_ms` (поведение продюсера при насыщении
очереди) и `control_event_processing_deadline_ms` (поведение актора после
получения события) — это два разных дедлайна на двух разных фазах, они никогда
не складываются в одну метрику (см. ТЗ 2.1). В коде это два отдельных
`Duration`-константы и два разных счётчика `actor_deadline_exceeded_total{phase=...}`.

## Sequence diagram: happy path buy

```
DEX program log (Geyser) → signal/dex_listeners/* → signal/dedup
    → actor::market_data_lane (или control_lane, если migration_event)
    → risk_gate::mod (параллельно: mint_freeze_authority, lp_lock_check,
       token2022_extensions, simulate_sell — доминант по времени)
    → sizing::kelly + sizing::adaptive → routing::mod (выбор DEX-адаптера)
    → signer_client (UDS) → solbot-signer::ipc_server
       → validation (allowlist program_id, max_size_absolute, hard_cap_bps,
          ipc_seq монотонность, issued_at_unix_ms возраст)
       → sequence_ledger (атомарно с audit_log, одна SQLite-транзакция)
       → signing → возврат подписанной tx
    → routing::jito_bundle (primary) | routing::public_rpc_fallback (degraded MEV, 3.6)
    → state::positions_repo (status: opening → open)
    → solbot-notify::events → solbot-telegram::alerts (Telegram MarkdownV2, 7.1)
```

## Sequence diagram: emergency exit escalation (2.3)

Единая эскалационная матрица (`exit/escalation.rs`) переиспользуется тремя
триггерами: hard SL, `on_backfill_incomplete` (2.4), `circuit_breaker.on_trigger`
(4.8). Реализована как явный state machine на 4 стадии (`Stage0Jito`,
`Stage1PublicRpc2x`, `Stage2PublicRpc3xMaxSlippage`, `Stage3DurableNonceStuck`),
переходы между стадиями — единственное место, где выпускается НОВАЯ подпись;
повторные попытки внутри стадии переиспользуют уже подписанную транзакцию —
см. doc-комментарий в `exit/escalation.rs` со ссылкой на 2.3 и 3.3 (вывод
signing-rate threshold опирается именно на это правило).

## Смысл каждого крейта одной строкой

| Крейт | Ответственность | Держит ключ? |
|---|---|---|
| `solbot-common` | Общие типы, тиры (Приложение A), конфиг, ошибки, OTel-хелперы | Нет |
| `solbot-strategy` | Вся торговая логика: сигналы, риск-гейт, сайзинг, exit, роутинг, circuit breaker, smart money watchlist consumption, состояние в SQLite | Нет — только строит неподписанные intent'ы |
| `solbot-signer` | Единственный держатель приватного ключа, IPC-сервер `signer.proto`, anti-replay, compromise detection, подпись | Да, mlock, systemd hardening |
| `solbot-notify` | Общая шина событий-алертов между процессами (без прямой зависимости strategy/signer от telegram-крейта) | Нет |
| `solbot-telegram` | Уведомления (7.1) + admin-команды оператора через Telegram (доп. к CLI) | Нет |
| `solbot-cli` | Тот же admin-функционал с терминала (6.) | Нет |

## Что документ ТЗ сознательно оставляет вне кода (1.1, Приложение B)

- Алгоритм выбора «хорошего» токена/пула — здесь только исполнение.
- Автоматическая оценка прибыльности произвольного кошелька — `wallet_watchlist`
  наполняется вручную оператором по чек-листу (см. `docs/WATCHLIST_REVIEW_PROCESS.md`),
  бот только подписывается на уже одобренные адреса.
- GUI как отдельный продукт — только Admin CLI и Telegram-команды.
