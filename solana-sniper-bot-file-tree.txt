# SOLANA_BOT — полное дерево файлов репозитория

Собрано из трёх источников: `ARCHITECTURE.md` (разбиение на процессы/крейты),
`tz-solana-sniper-bot-production.md` (разделы 1–7 + Приложения A/B) и
`1.md` (реальные записи ревью wallet watchlist по чек-листу 2.5 — легли в `data/`).

Условные обозначения типа файла в скобках. Комментарий `//` после файла —
привязка к разделу ТЗ, откуда взято требование.

## Логика привязки к источникам

- **Три крейта-процесса** (`solbot-strategy`, `solbot-signer`, `solbot-telegram`) + вспомогательные (`solbot-common`, `solbot-notify`, `solbot-cli`) — точное соответствие таблице «Смысл каждого крейта одной строкой» в `ARCHITECTURE.md`.
- **Каждая подпапка `solbot-strategy/src/*`** — это один блок-адрес из sequence-диаграммы happy path в `ARCHITECTURE.md` (`signal → risk_gate → sizing → routing → signer_client → state → notify`).
- **`exit/escalation.rs`** — единственный файл, реализующий эскалационную матрицу 2.3, переиспользуемую тремя триггерами (hard SL, `on_backfill_incomplete`, `circuit_breaker.on_trigger`) — как и написано в `ARCHITECTURE.md`, это не три копии логики, а одна точка правды.
- **`migrations/0001_core_schema.sql`** и **`proto/signer.proto`** взяты дословно по структуре из разделов 5.1/5.2 ТЗ.
- **`config/tiers/*.yaml`** — прямое отражение Приложения A (там же обоснование, почему плоские значения на все тиры некорректны, см. 1.2, 3.4, 4.8).
- **`data/wallet_watchlist/`** — единственное место, куда легло содержимое `1.md`: это не код, а курируемые оператором данные (2.5, Приложение B — «список, а не алгоритм»). `reviews/2026-07-29.md` — архив самого ревью (14 адресов, статусы/чек-листы/заметки как есть), `seed_wallet_watchlist.sql` — то же самое в виде INSERT для таблицы `wallet_watchlist` из 5.1.
- **`deploy/systemd/solbot-signer.service`** — единственный unit с полным hardening-профилем из раздела 6 (это самый чувствительный процесс, держит ключ в памяти).
- **`tests/chaos|property|load`** — прямое соответствие таблице KPI/SLA (1.3) и разделу 7.3: каждый файл — это один пункт из списка chaos-тестов ТЗ, а не абстрактный набор.

## Что сознательно не входит в дерево (по 1.1 / Приложение B)

- Модуль «оценки качества токена/пула» как отдельная альфа-модель — вне рамок ТЗ, документ описывает только исполнение.
- Автоматический скоринг прибыльности произвольного кошелька — `wallet_watchlist` только читается ботом, наполняется вручную (см. `docs/WATCHLIST_REVIEW_PROCESS.md`).
- GUI как отдельный продукт — намеренно нет `frontend/`, `web/` и т.п., только `solbot-cli` и `solbot-telegram`.
